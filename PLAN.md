## 1. Scope

### 1.1 Statements to formalize

To be filled in once a paper is chosen: one row per numbered
definition/lemma/theorem/corollary/proposition, with the paper label, a
condensed statement, the source section, the Lean name, and the owning phase
module.  The model is §1.1 of `PLAN.md` in `n4code_lean_dev`.

Selection guidance for the first project:

- prefer a paper whose main theorem has a short dependency chain;
- prefer statements about finite combinatorial objects (they are decidable, so
  small cases can be closed with `decide`/`native_decide`);
- check whether the paper's key step is a *construction* (formalizes as an
  algorithm plus a correctness proof) or an *inequality* (formalizes as
  arithmetic over `ℝ` or `ℕ`).

### 1.2 Out of scope (usually)

- Computational experiments reported in a paper (numeric tables, simulation
  plots) are evidence, not theorems.  Formalizing them means writing an
  executable algorithm in Lean plus a correctness proof — an optional
  extension, not part of the core.
- Motivation, examples and background sections are not formalized.

## 3. Formal model (design decisions)

### 3.1 Representation

Everything is a function on `Fin`:

```lean
abbrev Word (n : ℕ) := Fin n → Bool          -- {0,1}^n
abbrev Column (M : ℕ) := Fin M → Bool        -- one column of an (n,M) code
abbrev Code (n M : ℕ) := Fin n → Column M    -- an (n,M) code, column-major
def row (C : Code n M) (j : Fin M) : Word n := fun t => C t j
```

Why column-major: the paper's arguments change columns (flip one column, swap
two columns), so a code is stored as the list of its columns and the codewords
are recovered with `row`.

### 3.2 Performance

```lean
def dRow  (C) (j) (y) := hammingDist (row C j) y      -- d_j(y)
def dCode (C) (y)     := min_j dRow C j y             -- d_C(y)
def alpha (C) (d)     := #{y | dCode C y = d}
noncomputable def lambda (C) (ε) := (1/M) * ∑ y, (1-ε)^(n - dCode C y) * ε^(dCode C y)
```

### 3.3 Conventions to lock down early (and record in `Notation.md`)

- bit order (which index is the most significant bit);
- whether indices are 0-based or 1-based relative to the paper;
- whether `n` is the blocklength and `M` the number of codewords;
- the direction of a comparison (`UniversalBetter C₁ C₂` means *which* code is
  better) — a frequent source of silently wrong statements;
- the exact range of the channel parameter (`0 < ε < 1/2`).

## 4. Work breakdown

Phases are ordered by dependency, not by the paper's section order.

### Phase A — Infrastructure (`Definitions.lean`, `Basic.lean`) — DONE
Words, XOR, Hamming weight/distance and their algebra; `(n,M)` codes, `row`,

checks pinning the representation.

### Phase B — Paper-independent lemmas — DONE
`dCode_le_dRow`, `dCode_le`, and the XOR/Hamming lemmas in `Basic.lean`.

### Phase C — Modelling the paper (`Definitions.lean` + `Notation.md`) — TODO
All paper-specific objects: code classes, special sets/regions, extra

### Phase D — Statement catalogue (`Statements.lean`) — TODO
Every numbered paper result as a Lean statement, `sorry`-stubbed, tagged with
its paper label.

### Phase E…— Proof phases — TODO
One module per phase, following the paper's logical dependency order; each
phase ends with `lake build` green and a commit.

### Final — Assembly and documentation — TODO
Zero `sorry`; axiom audit; `VERIFICATION.md` report; README status table;
tagged release.

## 7. Risks & mitigations

- *Statement drift* (Lean statement ≠ paper statement) → `Notation.md` +
  the manual checklist in `CONSISTENCY.md`, reviewed at every commit.
- *A paper lemma is actually false or under-hypothesised* → record it in
  `Notation.md` §4 and the companion note; state the corrected version and
  keep both, as `DEVLOG.md` does for the reference project.
- *Long elaboration times* → minimal imports, small modules, avoid
  `import Mathlib`, prefer `decide` over `native_decide` for headline results.
- *Toolchain churn* → `lean-toolchain` + `lake-manifest.json` are committed;
  upgrading is a deliberate, separate commit.

## 8. Effort estimate

Rough, for a beginner working with an AI assistant: modelling a paper is a
few days; the statement catalogue is a day; proofs dominate and are highly
variable (a short paper with a combinatorial main theorem can still be weeks).
Start with one small numbered result to calibrate.
